# 已有账号重新登录的浏览器资料连续性

本变更只处理账号会话连续性和并发安全，不提供反检测、指纹伪装或发送成功率保证。

## 生效范围

Web 服务显式设置 `SPARKFLOW_LOGIN_PROFILE_CONTINUITY=1` 时，已有账号的「重新登录」可选择发送端原有的账号 Profile。未启用该开关的安装保持原来的临时登录流程。添加新账号仍使用隔离的临时登录目录，因为扫码前还不能可信地知道账号身份。

发送目标、消息候选、发送窗口、重试次数、未知结果屏障、接收人核验和发送端无头模式均不因这项功能改变。

## 部署前提

- 登录桌面必须是支持 `account_profile` 的版本，不能使用会忽略该字段的旧镜像。
- 登录桌面与发送端共享 `/opt/douyin-sparkflow/state/browser-profiles`。
- 登录桌面只额外挂载发送端已有的 `logs/browser-account-locks` 子目录，不需要访问整份账号存储、其他日志或 Docker socket。
- 两端对同一物理账号持有同一把 `.lock.guard` 文件锁；锁文件不能删除或重建以绕过占用。
- 已有账号 Profile 不得执行临时登录环境的启动/关闭清理。

## 操作边界

有效登录会话应被保留并提示可以保存登录态；被动读取二维码不能自动清除该会话。明确点击「重新扫码」才请求重新认证。取消或关闭工作区只关闭浏览器并释放资源，不删除账号的本地存储。

复用 Profile 并不代表可以跳过身份、记录引用、登录版本、归属和工作区票据检查；保存后的新登录版本仍会使旧发送会话失效。无法证实清理完成时，不应提前放开账号锁。

## 验证与回滚

先在无外网、临时资料目录和合成身份下验证 Cookies、localStorage 和 IndexedDB 的关闭后重开保留，以及账号锁互斥。真实账号的重新登录和之后的自然调度需要分别观察，离线测试不证明抖音接受消息或火花续上。

回滚时先关闭功能开关并恢复 WebUI、Compose 和登录镜像。已经使用过共用 Profile 时，**保留 `core/profile_cookies.py` 的未保存登录态拦截以及 `core/login_profile.py`**，直到所有 pending 标记都经可信的新登录保存消除；不能恢复会忽略 pending 标记的旧发送代码。不要恢复较旧的账号凭据或删除真实 Profile。具体部署状态和实际回滚路径以任务的激活记录为准，本文件不是部署完成证明。
